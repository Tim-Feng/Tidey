# Controlled restart preparation

The installed `tidey-remote-bridge` owns two local operations, handled before pairing stores, servers, subscriptions or transcript tailers are created:

- `--inspect-restart`: read-only fresh binding inventory (`tidey.restart-inventory/1`).
- `--prepare-for-restart`: reconcile through the existing descriptor publisher and call native `checkpoint_for_restart` (`tidey.restart-preparation/1`).

Preparation writes only supported current descriptor updates and the native saved graph. It never starts/stops agents, removes descriptors to hide missing evidence, edits registry files, resumes threads, or restarts macOS. The command exits 0 for technical readiness and 2 for typed blockers; JSON is the authority, not the exit code alone. `owner_review_required` is always true.

A complete inventory accounts for each source record as one canonical durable launch or a typed non-restoring record. Three kinds exist, each returned under `non_restoring_records`, retaining history and requiring owner review; arbitrary unknown panels and conflicts fail closed:

- `handoff_rollback_owner_review`: a same-base handoff rollback. It requires current pane options on the exact socket, matching workspace/panel, a valid handoff token and its surviving stable native panel.
- `superseded_same_wrapper_alias`: a stale Claude registry alias left by the same live wrapper after an in-process session change. The current UUID is read only from the last complete hook event of the one journal whose marker names that wrapper PID, and every record must postdate the process birth. This fixed the 2026-09-24 same-wrapper classification defect; it is not proof of the 2026-09-16 Genesis root cause.
- `owner_confirmed_retained_rollback`: a cross-carrier rollback that the same-base rule deliberately does not cover. It is accepted only through an explicit `--restart-owner-receipt <absolute path>` naming each retained record, its thread, PID and birth, the exact approved live rollback option, and the canonical native successor. The receipt is bound to process generations; any refresh invalidates it, so a new receipt must come from unchanged owner intent after fresh identities are read. A record that could restore normally can never be excluded this way.

Preparation reads fresh runtime metadata, publishes a complete desired inventory, compares exact desired/stored carrier content without revocation, fences identity again, and sends the entire observed descriptor inventory as `expected_descriptors` to the native checkpoint. Native state must be hydrated, revisions/binding/content unchanged and runtime evidence acknowledged. The save owner flushes using its existing driver, opens its actual SQLite database read-only, runs quick_check, decodes each workspace restoration node and compares it to the live capture plan. A final runtime fence detects changes during the checkpoint. No retry loop grants authority to overwrite a conflict.

The checkpoint returns descriptors and saved graphs for post-reboot identity comparison. It does not promise unchanged PIDs, pane numbers or app-server socket paths after restart. Inspect canonical durable IDs, topology and fresh ownership relationships instead. A new active turn or identity change invalidates the point-in-time result.

Typed blockers include incomplete_inventory, conflicting_writers, identity_changed, publication_failed, descriptor_changed, awaiting_runtime_evidence, restoration_not_ready, save_unavailable, database_unavailable, database_integrity_failed, saved_graph_invalid and saved_graph_mismatch. Transport or unsupported installed versions report failure; no fallback edits SQLite or forces flags.

The shared workflow lives at /Users/timfeng/GitHub/life-system/.skills/controlled-reboot/SKILL.md. It reuses clean-dev-resources measurements and delegates semantic boundaries to their owners. It does not decide whether to interrupt work, accept dirty changes, dismiss a prompt, resolve a pending review, or restart Monitor. Actual reboot remains human-supervised.

Deployment is separate: these source changes cannot activate the API in an already running production app/Bridge. Follow the explicitly authorized tidey-production-deploy workflow for installation; preserve current sessions and update long-lived wrapper processes only at their authorized restart boundary.

## Status (2026-09-24)

- **Implemented in source, not installed.** The installed production build predates these operations, so `--prepare-for-restart` and native `checkpoint_for_restart` are unavailable in production. Controlled reboot must report `product_capability_unavailable` until an authorized deployment installs them.
- **Current deployment authority** is the existing tidey-production-deploy workflow, including its app-owned Runtime lineage handoff. It is the only executable path. Since 2026-09-24 its maintained helpers verify native carriers (ancestry under the current iTermServer, product durable IDs, attach/fresh process generations), proven only by fixture tests so far; a native controller, a checkpoint without native evidence and any new typed problem in the first live preflight must still be reported before the first stop. The authoritative list is the “Native carrier support in the maintained helpers” section of `/Users/timfeng/GitHub/life-system/.skills/tidey-production-deploy/SKILL.md`.
- **Proposal only, not executable:** updating at a restart boundary, where one `prepare → stop → install → start → accept` sequence serves both reboot and update. It is not yet a contract because (1) nothing can install while the Mac is off, (2) after login the old Tidey and Bridge may start automatically and recreate archive holders before an install runs, and (3) quitting the GUI does not by itself end the Runtime tmux server or its agent wrappers. No boot/login agent, installer framework or hidden controller exists for it. Do not treat it as available or require a reboot for every deployment.
- **Superseded:** the task-local live no-interruption deployment runner (external controller handoff, same-UUID refresh of every wrapper, input injection and its inverse) was removed on 2026-09-24. Do not reconstruct or execute it; its archived copy exists only for review and recovery.

**Restoration scope.** An agent panel must resume its own durable conversation on its original stable panel; a missing agent descriptor is a failure and is never excused as a non-agent limit. A non-agent panel restores its workspace membership, position, cwd and kind, but not the memory of the program it ran: after a Mac restart an ordinary-tmux panel is recreated from its topology with fresh shells, and results must say "topology restored, program not restored" rather than report success. Active jobs, pending reviews, unsent drafts and approval prompts follow the owner boundary; a visible footer is not evidence that anything was saved.
